# Intel RST / IMSM RAID 5: возврат диска из `Non-RAID` в состав массива (`Failed` → `Degraded` → `Rebuild`)

[English](README.md) | [简体中文](README.zh-CN.md) | [日本語](README.ja.md) | [Deutsch](README.de.md) | [Español](README.es.md) | **Русский**

> Реальный проверенный случай: RAID 5 Intel RST из 4 дисков (том `DATABASE`, 24 ТБ).
> Прошивка пометила том как **Failed**, один диск остался в состоянии **`Non-RAID`**.
>
> Результат: **`Failed` → `Degraded` → `Rebuild` → том смонтирован, файлы читаются.**
> Без форматирования, без удаления тома, без инициализации. Полной резервной копии никогда не было.

---

## Кратко

Сбой был **исключительно на уровне метаданных**. Мы изменили **22 байта** внутри **одного
физического сектора 4 КиБ** в самом конце диска — и прошивка приняла его при следующей загрузке.
В области данных не изменено **ни одного байта**.

## Симптомы

| Где | Что видно |
|---|---|
| BIOS / UEFI RST (OROM) | Том есть, но `Failed`; возвращённый диск отображается как `Non-RAID` |
| Окно RST в Windows | Фантомная запись: **размер 0 байт, состояние «Потерян», контроллер/порт неизвестны**, серийный номер с суффиксом `:0` (напр. `VLK5JGVY:0`) |
| Сам диск | Физически исправен: ATA `IDENTIFY`, SMART, ёмкость в порядке |

## Причина

Intel RST хранит **MPB** (MetaData Parameter Block) в **конце каждого диска-члена**, и каждая копия
содержит **полное описание массива**. Когда диск пропадает, его запись не удаляется, а помечается
**сразу в трёх местах**:

| Поле | Значение при отсутствии диска | Смысл |
|---|---|---|
| `disk[i].status` | `0x00000006` (`CONFIGURED \| FAILED`) | слот есть, но мёртв |
| `disk[i].scsi_id` | `0xFFFFFFFF` | местоположение неизвестно |
| `disk[i].serial` | реальный номер + **`:0`** | не должен совпадать с физическим диском |
| `map.disk_ord_tbl[slot]` | установлен бит `0x01000000` | рассинхронизирован |

Сопоставление идёт по **16-байтовому полю серийного номера** через `strncmp`:
`"VLK5JGVY:0"` ≠ `"VLK5JGVY"`. Поэтому переподключение кабеля и перезагрузки **не помогают никогда**.

Состояние тома вычисляется из членов:

```
число отказов = слоты с битом FAILED ИЛИ с IMSM_ORD_REBUILD
RAID5 при 1 -> Degraded  /  при 2 и более -> Failed
```

Здесь было **два** (извлечённый диск и диск, рассинхронизировавшийся несколькими часами ранее) → постоянно `Failed`.

## Что было сделано

1. Все диски-члены отключены от материнской платы (контроллер не участвует).
2. Последние 64 КиБ каждого диска прочитаны **только на чтение** дважды, с сравнением и сохранением SHA-256.
3. **Найдено расположение MPB** — это не непрерывные 584 байта:
   - якорь (байты `0..511`) в `последний LBA − 1`
   - расширенная часть (байты `512..583`) в **первых 72 байтах** `последний LBA − 2`
   - обе внутри **одного физического сектора 4 КиБ** → нужен read-modify-write целого сектора.
4. Все четыре копии разобраны по таблице полей из открытого кода `mdadm`: три идентичны и корректны
   (поколение 763553), у извлечённого диска старая копия (763509) с **неверной контрольной суммой**.
5. Исправленная конфигурация собрана из самой свежей корректной копии, изменено только необходимое:
   поле номера → `"VLK5JGVY"`, `status` → `0x0000053a`, `scsi_id` → `0x00000000`,
   `disk_ord_tbl[2]` → `0x00000002`, `map_state` → `2`, `generation_num` → `763554`, КС пересчитана.
   **Не тронуто:** family, ID/имя/размер тома, число членов, уровень RAID, страйп, начало данных,
   `failed_disk_num`, записи других дисков и метка рассинхронизации у действительно отставшего диска.
6. Одна и та же 584-байтовая конфигурация записана **во все оставшиеся члены** (по одному RMW 4 КиБ),
   чтобы все копии стали **побайтово идентичными**.
7. Выполнена проверка чтением: весь сектор, контрольная сумма, идентичность диска.

Изменения: **22 байта** на извлечённом диске и **по 15 байт** на двух других — только в секторе
метаданных в конце диска.

## Результат

| Этап | Наблюдение |
|---|---|
| До | `Failed`, `VLK5JGVY` = `Non-RAID`, фантомная запись `VLK5JGVY:0`, `0 байт` |
| Загрузка только с 3 исправленными дисками | **`Degraded`**, `VLK5JGVY` снова член массива, отсутствует `VKJGM9XX` |
| Подключение отставшего диска | Автоматически начался **`Rebuild`** |
| Windows | Том 24 004 676 026 368 байт, **Healthy / OK**, смонтирован, файлы открываются |

## Предупреждения

1. **Ошибка необратима.** Резервной копии нет.
2. **Никогда не записывайте «сырой» блок из 584 байт** — только целый сектор 4 КиБ.
3. **Никогда не переводите том в `Normal`.** `Normal` — это утверждение, что все члены синхронны.
   Если диск реально отстал, он будет **молча возвращать устаревшие данные**, а все структурные
   проверки при этом пройдут. До настоящего rebuild честным состоянием является только `Degraded`.
4. **Не позволяйте Windows монтировать том на запись** до проверки: NTFS проиграет свой журнал.
   Используйте `mountvol /N` или `Set-Disk -IsReadOnly $true`.
5. Не запускайте `chkdsk /f`, пока не скопированы важные данные.
6. Не «пробуйте» многократно: каждое посещение OROM RST может перезаписать метаданные.
7. Ёмкость и размер сектора у разных моделей отличаются — **пересчитывайте, не копируйте числа.**

## О версиях прошивки

Обновление драйвера или программы RST **в Windows** не меняет сборку массива при загрузке.
Первым работает **OROM в BIOS**: он перечисляет диски, определяет состояние и пишет метаданные.
Поэтому исправление использует формат MPB `1.3.00`, который нативно понимают OROM 19.x, и поэтому
настоящее исправление ошибки отключения Intel может прийти только как обновление BIOS от производителя платы.
